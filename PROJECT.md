## Модуль raw/ — обёртка LibRaw

Конвейер C API: `libraw_init → libraw_open_file → libraw_unpack (один раз!)
→ смена params → libraw_dcraw_process (повторно) → libraw_dcraw_make_mem_image
→ libraw_dcraw_clear_mem → libraw_close`.

- **Повторная проявка одним `Developer`**: `unpack` выполняется один раз
  (флаг `unpacked`), дальше только смена `params` + `dcraw_process`.
  Подтверждено тестом `develop_test.v`. Это даёт ~0.1 с на half-size
  вместо ~0.6 с с открытием файла.
- **C-структуры объявлены частично**: только используемые поля, с атрибутом
  `@[typedef]` (в libraw анонимные struct-typedef). Раскладку C-компилятор
  берёт из `<libraw/libraw.h>`, порядок/полнота полей в V-декларации не важны.
  Новое поле нужно сначала объявить в `C.libraw_output_params_t`.
- **Выход всегда линейный 16-битный**: `output_bps = 16`,
  `gamm[0] = gamm[1] = 1.0` (линейная гамма), `no_auto_bright = 1`.
  Даёт линейный 16-бит RGB в sRGB-праймерис с камерным ББ — сырьё для
  пайплайна (`DevImage.data_u16()`). 8-битного режима с гаммой и
  авто-яркостью (им пользовался убранный CLI) больше нет.
- **Пересветы** (`DevParams.highlight`, аналог dcraw -H): 0 — клип (дефолт),
  1 — без клипа, 2 — смешение, 3..9 — реконструкция (меньше — белее,
  больше — цветнее). Работает на этапе dcraw_process — до потери клипнутых
  каналов, поэтому в пайплайне это не воспроизвести. Смена режима требует
  перепроявки (re-unpack НЕ нужен). Тест `highlight_test.v` — режимы 0/2/5
  дают разные данные на передержанном кадре.
- `DevImage` владеет C-буфером LibRaw — после использования обязателен
  `free()`. `data()` — как &u8, `data_u16()` — как &u16 (только при bits == 16).
- **`thumb()`** — встроенное превью камеры как байты JPEG (Canon кладёт
  полноразмерный JPEG с камерной обработкой): `libraw_unpack_thumb` +
  `dcraw_make_mem_thumb`, наружу отдаётся копия. Поле `type` C-структуры
  недоступно (`type` — ключевое слово V), JPEG распознаётся по сигнатуре
  FF D8. Используется для камерной кривой (`pipeline.match_curve`).
- **`decode_jpeg(data) !Jpeg`** (`jpeg.v`, 06.10.2026) — JPEG в RGB через
  libjpeg-turbo (LibRaw и так с ним слинкован, `#flag -ljpeg`), выход —
  в bigbuf (`Jpeg.pix`, освобождать `free()`). C-прослойка
  `raw/jpeg_shim.h`: ошибки libjpeg — `longjmp`, поэтому `setjmp` и весь
  разбор — в C (первый вызов — размер, второй — пиксели в буфер V).
  Полный JPEG камеры (24 Мп, 72 МБ) раньше декодировал stbi — в кучу
  сборщика на каждое открытие кадра. Пиксели от stbi отличаются в
  пределах IDCT (тест `jpeg_test.v`: средняя разница < 1 уровня;
  испорченный и обрезанный файл — ошибка или серое, без падения).
- **Half-size при нечётном размере кадра** (R8: 5999×3999): LibRaw
  округляет вверх, последняя ячейка Байера неполная — крайние столбец и
  строка без синего (B = 0), на превью оранжевая полоса, которую geometry
  ещё и размазывает. `develop(half)` режет их (`crop_half_edge`): размер
  «вниз» (полный / 2, превью 2999×1999), сдвиг строк на месте в буфере
  LibRaw. Полный размер кадра снимается в `open()` (`full_w/full_h`, с
  учётом `sizes.flip`) — после half-проявки LibRaw держит в `sizes` уже
  уменьшенные значения. Тест `half_edge_test.v`. Полная проявка не
  затронута.
- Ошибки LibRaw → текст через `libraw_strerror` + `cstring_to_vstring`.
- **`meta()`** (`Meta`): производитель и модель камеры (раздельно:
  «Canon», «EOS R8»), объектив и его производитель (`LensMake`, у CR3
  пуст), фокусное, диафрагма, выдержка (с), ISO, автор из EXIF камеры,
  дата съёмки (`timestamp`). Для профиля объектива и EXIF готового файла.
- **`color()`** — цвет камеры для баланса белого (`ColorData`): `cam_mul`
  (множители «как снято»), `rgb_cam` (камера после ББ → линейный sRGB),
  `cam_xyz` (XYZ → камера, Adobe ColorMatrix). Заполнены уже после
  `open()` — проявка не нужна. У R8: cam_mul 2068/1024/1436.
- **Встроенные превью**: `thumb()` — самое большое (полный JPEG камеры):
  при непустом `thumbs_list` — явно `thumb_min(1 << 30)`, потому что голый
  `unpack_thumb` отдаёт ПОСЛЕДНЕЕ выбранное превью (после `thumb_min(1000)`
  — 1620×1080; так фоновый загрузчик GUI какое-то время строил камерную
  кривую не по тому превью — тест `test_thumb_after_thumb_min_and_develop`);
  `thumb_min(min_side)` — наименьшее превью с длинной стороной ≥ min_side
  из `thumbs_list` (у CR3 три: 160×120, 1620×1080 и полное — в списке
  0x0, считается самым большим) через `unpack_thumb_ex(idx)`; извлечение
  0–3 мс. **`unpack_thumb_ex` после `dcraw_process` LibRaw 0.21 запрещает**
  (код -4, out of order; обычный `unpack_thumb` — можно): тогда
  `thumb_min` открывает файл вторым хендлом (1–6 мс). `flip()` — ориентация
  кадра (`sizes.flip`: 3 — 180°, 5 — 90° против, 6 — 90° по часовой);
  превью лежат в ориентации сенсора. Тест `thumb_test.v`. **Превью
  1620×1080 для камерной кривой не годится**: у CR3 оно обработано иначе
  (на IMG_0817 света кончаются на 223 из 255, кривая по нему — тусклые
  света; на других кадрах разница 1–14 из 255), поэтому камерная кривая
  (`camera_curve` в `loader.v`) — только по полному `thumb()`.

## Модуль lens/ — коррекция объектива (lensfun)

- **База загружается один раз за запуск**: `lens.load_db()` (~115 мс —
  XML всех профилей) → `&Database`, поиск `db.find(make, model, lens)` —
  сотые доли мс. База не меняется, поиск и коррекция её только читают —
  одну базу используют загрузка кадра и сохранение из своих потоков.
  `Corrector` из `db.find` базу не освобождает (`free()` — только
  обнуление); `lens.find()` — разовый вариант со своей базой (тесты),
  такой `Corrector` владеет базой и освобождает её в `free()`. GUI:
  `st.lens_db` грузится в начале main, освобождается на выходе после
  всех воркеров. Тест `test_shared_database`.

Обёртка над liblensfun 0.3.4 (apt, `liblensfun-dev`). Две коррекции:
`vignetting()` (карта усиления) и `geometry()` (дисторсия + TCA одним
субпиксельным ремапом). Порядок строгий: сначала vignetting, потом
geometry — виньетка привязана к исходной геометрии сенсора.

- **Поиск профиля**: `lens.find(cam_make, cam_model, lens_model)` по строкам
  из `raw.Developer.meta()` (аксессоры `libraw_get_iparams/lensinfo/imgother`).
  ВАЖНО: LibRaw отдаёт make/model раздельно («Canon», «EOS R8»), а в базе
  lensfun модель полная («Canon EOS R8») — матчеру нужен запрос, покрывающий
  её целиком, поэтому вторая попытка с приклеенным производителем
  (приём darktable). Указатели cam/lens живут внутри db → база держится
  открытой всю жизнь `Corrector`, освобождение только в `free()`.
- **База профилей**: системная (0.3.4, 2022 год) НЕ содержит RF 24-50 и
  RF-S 18-45. Свежая база формата version_1 лежит в
  `~/.local/share/lensfun/updates/version_1` (скачана с
  lensfun.github.io/db/version_1.tar.bz2; master на GitHub — формат 2,
  0.3.4 его не читает). Рядом обязателен `timestamp.txt` (unix-время) —
  без него lf_db_load предпочтёт системную базу и профиль не найдётся.
- **Вырожденные профили**: полином виньетирования «pa» у RF 24-50 (24 мм,
  f/6.3: k1 −0.17, k2 −1.77, k3 0.90 — та же запись и в базе RawTherapee
  5.12) растёт к краю как ×1.68 на 0.7 радиуса, ×3.5 на 0.85, ×16.7 на
  0.95 и в углу проходит через «полюс» в ноль и минус — прямое
  применение lensfun к u16 даёт чёрные (или выбитые) углы. Поэтому
  `vignetting()` снимает карту усиления в f32 (коррекция единичного
  буфера, `LF_CR_1(INTENSITY)`) и строит из неё **радиальный профиль**
  (`vign_profile`, `vign_lut_n` = 1024 точки от центра до угла по
  диагонали, значения карты билинейно — ближайший пиксель давал дрожь):
  - **неубывающий**: NaN, ноль, спад — «полюс», дальше держится значение
    до него (раньше спад давал светлые серпы у углов);
  - **мягкий потолок** `soft_cap` в лог-домене: до `vign_knee` = 8 как
    есть, выше `knee·(cap/knee)^tanh(...)` — плавно (C1, без излома) к
    `vign_cap` = 16 (раньше жёсткий потолок ×8 давал излом — дугу на
    небе);
  - **ослабленный**: `g^strength` — сила кадра (параметр `vignetting()`,
    подбирается по JPEG камеры, см. ниже; по умолчанию `vign_default` = 0.3).
  Буфер умножается по профилю по расстоянию пикселя от центра
  (`apply_radial_gain`, линейная интерполяция профиля, строки в потоки).
  Модели виньетирования lensfun радиальны — профиль по диагонали
  описывает всю карту.
- **Перекоррекция («вывернутая виньетка»)**: профиль RF 24-50 завышен уже
  с 0.7 радиуса — при полной силе края неба светлее центра и у углов
  светлый ореол (проверено и с гладким профилем 01.10.2026). Поэтому сила
  в ЛОГ-домене меньше 1. До 02.10.2026 — одна константа 0.3 на все
  объективы (подобрана на глаз на `IMG_0817.CR3`), теперь — своя у кадра
  по встроенному JPEG (ниже). История «ступенчатого неба» на этом кадре —
  в разделе pipeline/, пункт «Камерная кривая».
- **Фрагмент кадра** (03.10.2026, для настоящего 1:1): виньетирование
  разделено на профиль кадра `vign_lut` (один на кадр, ~130 мс на 24 Мп)
  и умножение `vign_apply_region` по куску (усиление — от центра ПОЛНОГО
  кадра); дисторсия + TCA — `GeomPlan` (`geometry_plan`: модификатор с
  подобранным масштабом), `source_box(r)` — какой кусок источника нужен
  выходу r, `remap` — ремап r из куска. `vignetting`/`geometry` полного
  кадра идут тем же кодом (весь кадр — один прямоугольник), поэтому
  фрагмент побитово равен вырезке (тест `test_region_matches_full`).
  **Грабли lensfun:** `lf_modifier_apply_subpixel_geometry_distortion`
  считает точки строки накоплением от начальной и блоками по 4 с
  отдельным хвостом — строка, начатая с x > 0 или другой длины, даёт
  другие координаты (до 0.2 px). Поэтому `row_coords` всегда берёт ВСЮ
  строку кадра, фрагмент — свой кусок из неё (фрагмент 1100×900 полного
  кадра: кусок ~45 мс, виньетка + ремап ~63 мс).
- **Кадр «как у камеры»** (05.10.2026; `geometry_plan_zoom`,
  `geometry_zoom`, `effective_scale`; `lens_match` в `loader.v`). После
  исправления дисторсии камера обрезает кадр сильнее автомасштаба lensfun
  (RF 24-50 на 24 мм — на 8.5%, RF 24-105 на 24 мм — на 4.9%, RF 24 —
  на 2.2%, на длинных концах ~0–1.6%): JPEG выглядел «кропнутым». Масштаб
  совмещения из подбора силы виньетки (`align_zoom`, ниже) — это и есть
  увеличение кадра «как у камеры»: `LensMatch.zoom` (не меньше 1, иначе
  пустые углы; < 1.002 — 1; потолок `frame_zoom_max` = 1.2), путь —
  `CamLook.zoom` → `EditState.lens_zoom` (производное, в сайдкар не
  пишется) → `PrepJob.zoom` (превью), `correct_lens(…, zoom)` (экспорт,
  пакет), `make_detail_lens(…, zoom)` и ключи 1:1. Важное: lensfun 0.3.4
  в авторежиме масштабирует, но `lf_modifier_get_auto_scale` возвращает
  1 — настоящий масштаб ищет `effective_scale` (двоичный поиск явного
  масштаба, при котором точка у края кадра уходит туда же, что в
  авторежиме; на 105 мм RF 24-105 — 1.010, RF 100-400 на 400 мм — 1.017).
  Проверено: на всей базе lensfun (1522 объектива с дисторсией, по 3
  фокусных) совпадение с авторежимом точнее 0.05 px, кроме циркулярных
  фишаев Sigma 4.5/8 мм (поиск упирается в границы → 0 → авторежим без
  увеличения); на 148 RAW (6 объективов) кадр после увеличения совпадает
  с JPEG в пределах 0.5% у 146 (два кадра RF 100-400 на 400 мм: камера
  на 1.1% шире автомасштаба — расширять нельзя). Тест
  `test_effective_scale`, в `vign_test.v` — увеличение IMG_0817 ~1.085.
- **Сила по JPEG камеры** (02.10.2026; `lens/match.v` + `lens_match` в
  `loader.v`): спад яркости к краю после коррекции — как у JPEG этого же
  кадра. ~80 мс на превью (-prod), в загрузчике, до коррекции объектива.
  - **Рабочая копия** (`match_frame`): сырьё без коррекции уменьшается до
    `match_side` = 512 по длинной стороне (`box_down`) и проходит
    `geometry()` (JPEG камеры исправлен по дисторсии); карта усиления
    полного профиля (ровное поле 4000 в u16 через `vignetting(…, 1.0)`)
    проходит ту же geometry — в каждой точке ln усиления ИСХОДНОЙ точки
    сенсора. Кадр с силой s — копия × gain^s (`with_strength`), geometry
    на каждую пробу не нужна.
  - **Совмещение** (`VignRef.new`, `align_zoom`): камера кадрирует
    сильнее авто-масштаба lensfun — у RF 24-50 на 24 мм JPEG крупнее
    в 1.084 раза, у RF 24-105 на 105 мм — в 1.011. Без совмещения на краю
    сравнивались разные места сцены (десятки пикселей копии), оценки
    скакали от размера копии. Масштаб — перебором 0.85..1.25 (шаг 0.01,
    затем 0.001) по корреляции люм (наша — гамма при силе по умолчанию);
    корреляция ниже 0.6 — сила по умолчанию. Точки за кадром JPEG, у его
    края (2 px) и с каналом JPEG от 250 не сравниваются. JPEG другой
    пропорции (обрезан) — сила по умолчанию.
  - **Оценка** (`VignRef.fit`) — без тоновой кривой: JPEG — глобальная
    монотонная кривая от линейной яркости, значит у точек одного тона JPEG
    (корзина люмы 16..235) одинакова и наша яркость после коррекции
    `y + s·l` (y — ln нашей люмы без коррекции, l — ln усиления).
    Регрессия с фиксированными эффектами корзин:
    `s = −Σ(y−ȳ)(l−l̄) / Σ(l−l̄)²`. Содержимое сцены сокращается (небо в
    центре и тень у края не дают ложного спада). Надёжность: от 4000
    точек и СКО l внутри корзин ≥ 0.03, иначе сила по умолчанию; пределы
    0..1.2.
  - **Что пробовали и отказались**: подбор по ровности разницы с JPEG
    по кольцам ПОСЛЕ нашей камерной кривой — кривая по гистограммам
    скачет от малой смены силы, целевая функция рваная (0817: 0.25 или
    0.475 в зависимости от размера копии).
  - **Итог** на тестовых кадрах (R8): IMG_0817 (RF 24-50, 24 мм, f/6.3)
    0.51, IMG_0634 (тот же объектив, f/5.6) 0.26, IMG_0991 (RF 24-105,
    105 мм) 0.58; локальная сила по кольцам радиуса ровная (0817:
    0.45–0.62), значит форма профиля в целом верна, ошибается его
    величина. На 0817 углы неба при 0.51 — как у камеры (верхняя строка
    73→75 против 85→75 у JPEG и 67→73 при 0.3), ореола нет.
  - Хранится в `CamLook.vign` → производное поле снимка `EditState.vign`
    (`with_derived`, в сайдкар не пишется): превью — `PrepJob.vign` из
    `st.look`, экспорт — `correct_lens(…, e.vign)`, пакет —
    `batch_derive` при коррекции объектива. Считается и при выключенной
    коррекции (профиль найден) — включат без перезагрузки. Тесты
    `vign_test.v` (синтетика: регрессия восстанавливает 0.6, ровное поле
    — без оценки, совмещение находит масштаб 1.08; IMG_0817 — 0.4..0.6) и
    `test_match_frame` в `lens_test.v`.
- Виньетирование корректируется строго в ЛИНЕЙНОМ пространстве до
  пайплайна — это физическое затемнение. Профиль намеренно НЕ закрывает
  весь перепад RF 24-50 в углах (реально там 5+ EV — круг изображения еле
  накрывает сенсор): остаток убирает geometry(), которая, как камера и RT,
  выносит мёртвые углы за рамку.
- **geometry()**: `lf_modifier_initialize` со `scale = 0.0` (авто-масштаб —
  без него после исправления бочки остались бы пустые края) и флагами
  `LF_MODIFY_DISTORTION | LF_MODIFY_TCA | LF_MODIFY_SCALE` (1, 8, 0x20).
  **Без LF_MODIFY_SCALE lensfun молча игнорирует scale** (и авто, и
  заданный) — так и было до исправления: рамка кадра смотрела за
  источник, после клампа край — 3–4 повторённых столбца (на подушке
  RF 24-105 при 105 мм). Авто-масштаб lensfun к тому же приблизительный
  (lensfun.h: «sometimes a little less than optimal»), поэтому после
  инициализации `border_overflow` меряет, во сколько раз рамка (крайние
  строки/столбцы, все каналы) вылетает за источник, и при > 1 модификатор
  пересоздаётся с `scale = auto · вылет · 1.001` (до двух шагов);
  `lf_modifier_apply_subpixel_geometry_distortion` зовётся ПОСТРОЧНО
  (буфер координат w×3 пары; на весь кадр было бы сотни МБ), даёт пару
  (x, y) источника на каждый канал — разница пар между каналами и есть
  коррекция TCA. Выборка — своя билинейная по копии источника, координаты

## Модуль pipeline/ — тональный пайплайн

Вход: плотный линейный 16-бит RGB (`&u16`, npix пикселей). Выход: 8 бит,
`dst_stride` 4 = RGBA для холста (альфа 255) или 3 = RGB для JPEG.

### Порядок операций и формулы

Обозначения: `c` — линейное значение канала 0..1, `Y` — линейная люма,
`t` — тоновая позиция, `v` — тоновое (гамма-кодированное) значение 0..1.

0. **Удаление дымки** (`dehaze.v`, только `apply_image` с картой, при
   `haze != 0`): `c' = (c − A)·k + A` по линейному сырью, k — из таблицы
   по карте дымки; см. ниже.
0½. **Баланс белого** (`wb.v`, при `wb_on`): `Params.wb` (`WbXform`) по
   линейному сырью «как снято» — матрица, у светов по шагам с клипом в
   пространстве камеры; при дымке или ББ люма для масок
   считается во f32 уже после них. См. «Баланс белого» ниже.
1. **Экспозиция**: множитель `E = 2^exposure` (EV) в линейном пространстве.
2. **Люма** (для масок): BT.709 `Y = 0.2126 R + 0.7152 G + 0.0722 B`.
   В коде — целочисленно: `(54 R + 183 G + 19 B) >> 8` (54+183+19 = 256).
3. **Тоновая позиция**: `t = clamp01(Y·E)^(1/2.2)` — люма ПОСЛЕ экспозиции,
   в перцептивной (гамма) шкале, чтобы полосы эквалайзера легли равномерно.
4. **Тени**: добавка в EV `shadows · (1−t)²` — маска 1 в черноте, 0 в белом,
   гладко затухает. Диапазон ползунка ±4 EV.
5. **Тон-эквалайзер**: 5 узлов (чёрные/тени/средние/света/белые) на
   t = 0, 0.25, 0.5, 0.75, 1 с линейной интерполяцией (tent-базис) →
   добавка `eq_ev(t)` в EV. Ползунки ±4 EV.
6. **Общий множитель** пикселя: `k = E · 2^(shadows·(1−t)² + eq_ev(t))`,
   применяется к каналам ЛИНЕЙНО и одинаково для R,G,B — маска по люме,
   а не по каналу, поэтому подъём теней не сдвигает цвет.
7. **Гамма**: `v = (c·k)^(1/2.2)` (упрощённая sRGB; клип к 1.0 до степени).
7½. **Камерная кривая** (`Params.curve`, 256 узлов тон→тон, линейная
   интерполяция; пустой массив = тождественная): применяется после гаммы,
   до контраста. Строится `match_curve()` — гистограммное сопоставление
   нейтральной проявки со встроенным JPEG камеры (приём «Автоопределение
   тоновой кривой» RawTherapee): CDF тонов обоих кадров, тону v источника
   назначается тон JPEG той же квантили (тона, которых в кадре нет, — без
   соответствия), затем `fit_curve` — гладкая кривая (см. «Ступенчатое
   небо» и «Блёклая проявка» ниже). Кадры могут быть разного размера,
   гистограммы сэмплируют каждый 4-й пиксель. ИМЕННО ЭТО отвечает на
   «почему при одинаковой экспозиции RT светлее»: нейтраль vraw — чистая
   гамма 2.2, а RT по умолчанию накладывает кривую под камерный JPEG
   (+1..3 EV в средних).

   **Применение — смесь по каналам и по люме (05.10.2026, `CamTone`,
   `cam_tone_px`, доля `cam_curve_lum` = 0.5).** Тоны каналов по гамме
   `t_c` и по гамме с кривой `C(t_c)`; люма тонов `l`; результат
   `0.5·C(t_c) + 0.5·t_c·C(l)/l`. Почему не просто по каналам: кривая по
   каналам сжимает каждый канал отдельно и в светах, где у камерной
   кривой «плечо», выбеливает цвет — на передержанных кадрах света у JPEG
   насыщеннее нашего (ΔC Lab +4.5, сильнее всего у почти серых пикселей),
   а тени, наоборот, бледнее (−1.4). Замер на 46 кадрах (19 передержанных
   + 27 обычных; ΔE Lab по строкам, не участвовавшим в подгонке, оба кадра
   размыты на 1.5 px — без краёв, резкости и шума JPEG, иначе половина ΔE
   — не цвет), с таблицей цвета по оттенку:
   | способ кривой | передержанные (света) | обычные |
   |---|---|---|
   | по каналам (было) | 3.30 (5.63) | 2.10 |
   | RGB-тон как Film-like Adobe (max/min через кривую, средний держит оттенок) | 3.16 | 2.06 |
   | по люме | 2.62 (3.58) | 2.11 (света хуже: 3.41) |
   | **смесь 0.5** | **2.47 (3.34)** | **1.79** |
   Смесь лучше у 44 кадров из 46, хуже — ни у одного заметно (IMG_0375
   +0.03). Доля, подобранная по кадру, почти ничего не даёт (2.88 против
   3.14 без таблицы), поэтому она постоянная — цвет не «прыгает» между
   кадрами серии. Насыщенность `match_saturation` и таблица цвета
   подгоняются уже по смешанной кривой. Серое смесь не меняет (оба
   способа на сером совпадают), тест `test_camera_curve_blend`.

   Устройство в рендере: при камерной кривой `flut` делится на две части —
   `CamTone.gc` (65536 пар «гамма, гамма + кривая», рядом в одной строке
   кэша; гамма — константа `gamma_lut`, считается при запуске) и множитель
   люмы `CamTone.kl` (доля × C(l)/l по тону × 16, у чёрного < 0.5 — как у
   0.5); после смеси — таблица тон → тон `build_post` (контраст, на неё
   `channel_luts` накладывает тональные кривые; шаг 1/16 тона, без
   контраста и кривых — не строится). Порядок «кривая → контраст →
   тональные кривые» прежний. Стоимость на превью IMG_0991 (6 Мп, -prod):
   14.9 → 22 мс, с контрастом 16.7 → 26 мс.

   **Ступенчатое небо (IMG_0817.CR3, 01.10.2026) — проблема и решение.**
   Симптом: на гладком небе (RF 24-50, 24 мм, f/6.3) над горизонтом
   светлый купол с заметной границей, выше — небо резко темнее и уходит
   в бирюзу, у верхних углов светлые серпы; JPEG камеры гладкий и ровно
   синий. Разбор (замеры по радиусу от центра, вычитание размытой копии —
   локальные перепады, отключение по одному звену):
   - **Главная причина — камерная кривая.** Прежняя кривая была просто
     соответствием квантилей, слегка сглаженным (box r=2), и повторяла
     каждую неровность распределения. Небо на полкадра — большой пик
     гистограммы в узком диапазоне тонов; у IMG_0817 на тонах 104–120
     (как раз небо) наклон ×3.5–4.6 при ×1 рядом. Малые перепады неба
     растягивались в 4–5 раз, изломы на 104 и 120 видны как границы
     ступеней, а поканальное применение кривой давало оттенок, зависящий
     от яркости (бирюза/синева). Без кривой небо гладкое и ровное по
     оттенку (тускло). Решение — `curve_from_mapping` (своя реализация):
     опорные точки через `curve_step` = 32 тона (значение — среднее
     соответствия в ±2 тонах, пусто — ближайший тон с данными в ±8, нет и
     его — точки нет); `limit_slopes` — наклоны соседних отрезков
     ломаной различаются не больше чем в `curve_slope_ratio` = 2 раза
     (средняя точка тянется на четверть пути к хорде соседей, до 200
     проходов); монотонный кубический сплайн Фрича–Карлсона
     (`monotone_spline`) — гладкий, без выбросов, не убывает. Кривая
     IMG_0817 стала плавной S (наклон 0.8→2.35→0.39), у IMG_0991 и
     IMG_0634 почти не изменилась (визуально так же близко к камере).
     Тесты: `test_camera_curve` (восстановление известной кривой sqrt
     по гистограммам — точность ±8 тонов) и
     `test_curve_from_mapping_smooth` (скачок ×5 на 16 тонах в кривую не
     проходит: наклон < 3, соседние участки — без излома). С 05.10.2026
     опорные точки заменены сглаживающим сплайном (см. ниже).
   - **Вторая причина — коррекция виньетирования** (см. модуль lens/,
     `vignetting()`): жёсткий потолок ×8 давал излом карты, спад
     вырожденного профиля за «полюсом» — серпы в углах. Теперь профиль
     радиальный, неубывающий, с мягким потолком; сила ослаблена:
     при полной силе профиль RF 24-50 перекорректирует с 0.7 радиуса
     (края неба светлее центра, ореол у углов). Сначала была константа
     0.3, с 02.10.2026 сила подбирается по JPEG камеры (на этом кадре
     0.51) — см. модуль lens/, «Сила по JPEG камеры».
   - Что НЕ было причиной (проверено, чтобы не искать снова): полосы
     квантования 8 бит (дизеринг работает, в столбце неба шаги по 1–4
     пикселя; тонкие концентрические полосы при ×12 контраста есть и в
     JPEG камеры — это уровни 8 бит), интерполяция исправления дисторсии
     (без `geometry()` картина та же), обрезка u16 при усилении (неба
     у белого нет).
   - RawTherapee 5.12 на этом кадре гладкий, но блёклый: в профиле
     пользователя нет кривой под JPEG. Его база lensfun с тем же
     профилем RF 24-50. Код RawTherapee (GPL) не использовался —
     кривая и профиль виньетки написаны заново.

   **Цвет «как JPEG» (05.10.2026)** — `pipeline/camhue.v`. Кривая и общий
   множитель насыщенности повторяют тон камеры, но не цвет: у Canon
   («Стандарт») голубые (небо) насыщеннее нашего в ~1.46 раза по
   Lab-хроме, зелень сдвинута на +8° к голубому, жёлто-оранжевое — на −7°;
   разброс по кадрам большой (хрома сектора ×0.63…×1.22) — таблица своя
   у кадра. `match_hues`: рабочая копия (`camera_hues` в loader.v: сырьё
   после объектива, `lens.downscale` до 512, `apply` с кривой и
   насыщенностью) против JPEG, вписанного в тот же размер (кадр совмещён
   увеличением «как у камеры»). Таблица — оттенок × яркость ×
   насыщенность (с 05.10.2026, вторая версия; первая была только по
   оттенку): 24 сектора HSV-оттенка по 15° × 4 полосы яркости V (по 64) ×
   3 полосы насыщенности HSV (центры 0.05 / 0.15 / 0.35) = 288 ячеек,
   индекс `(l·3 + s)·24 + k`. Зачем яркость и насыщенность: в светах
   камера поднимает насыщенность почти серого в 1.5–2.5 раза, чистых
   цветов — в ~1.1 (как «сочность»), тени у неё бледнее наших; таблица по
   одному оттенку этого не повторит. Подгонка — по блокам 2×2 строк
   y%4 ∈ {0,1} (усреднение гасит шум и остаток совмещения; точки с
   насыщенностью от 0.03, яркостью от 25, блок не у клипа 250): сдвиг
   оттенка (секстанты) — наименьшими квадратами с весом насыщенности (как
   применяет эквалайзер), множитель насыщенности — отношение. Стягивание
   по уровням с весом n/(n+75): сектор → «без изменений», сектор × полоса
   яркости → сектор, ячейка → сектор × яркость; сглаживание [1,2,1] по
   всем трём осям (по оттенку — по кругу), пределы ±30° и ×0.6…×1.6.
   Проверка по строкам y%4==2: средний ΔE Lab не уменьшился на 2% —
   таблицы нет; строки y%4==3 — для внешней оценки. Путь:
   `CamLook.hue/hsat` → `with_derived` (при «Как JPEG») →
   `Params.cam_hue/cam_hsat` → `hsl_pixel` (не в таблице эквалайзера —
   зависит ещё от яркости и насыщенности пикселя): `cam_lookup` —
   трилинейно (два сектора × две полосы яркости × две насыщенности),
   складывается с ползунками HSL (сдвиг взвешен насыщенностью пикселя,
   множитель — нет). Ползунки HSL не двигаются: таблица — базовый слой,
   как кривая. Проверка (46 кадров: 19 передержанных + 27 обычных; ΔE по
   строкам вне подгонки, размытие 1.5 px — см. п. 7½), поверх смешанной
   кривой: только по оттенку 2.47 / 1.79 → 2.20 / 1.61 (света
   передержанных 3.34 → 2.67), лучше у 45 кадров, хуже — ни у одного;
   таблица у всех 46. Стоимость на превью 6 Мп (-prod): ~+21 мс (кривая
   23 → 44 мс; по одному оттенку было ~+13). Тест `test_match_hues`.
   (Первая версия на 37 кадрах: 3.31 → 2.98, небо IMG_0817 8.25 → 3.62.)

   **Блёклая проявка (05.10.2026) — проблема и решение.** Симптом: при
   переключении кадра встроенный JPEG (быстрое превью) сменялся заметно
   более плоской проявкой RAW. Причина — прежнее сглаживание кривой
   (опорные точки через 32 тона + перепад наклонов не больше ×2): оно
   не может повторить камерный «носок» в тенях (почти плоско у чёрного,
   потом круто вверх) и поднимало чёрный, а на крутых участках (небо)
   занижало кривую. Решение — `fit_curve(mapping, hs)` (своя реализация;
   идея плотности «густо в тенях, редко в светах» совпадает с RawTherapee,
   у него ~8 неравномерных опорных точек): сглаживающий сплайн на всех
   256 тонах — минимум Σ w·(c − mapping)² + λ(v)·(вторая разность c)²,
   вес w — корень из доли пикселей тона (масштаб — как у превью 6 Мп с
   выборкой каждого 4-го пикселя), λ = `curve_lam_shadow` (300) в тенях и
   `curve_lam` (50000) выше `curve_soft_edge` (тон 40), переход за
   `curve_soft_band` (16) тонов; концы (0,0), (255,255) закреплены;
   пятидиагональная система — Гаусс по ленте; затем монотонность.
   `curve_from_mapping(mapping)` — то же с равными весами (тест).
   Проверка на 148 RAW с диска (превью тем же путём, что окно; перцентили
   яркости против встроенного JPEG): среднее отклонение по перцентилям
   2/5/25/50/75/95% — было 7.8/7.2/3.4/2.3/3.5/5.9 уровня (худшее до 57),
   стало 0.9/1.6/1.9/1.0/0.8/1.1 (худшее 7); небо IMG_0817 — гладкое,
   без ступеней (контраст ×N).
8. **Контраст**: S-кривая (bias/gain) `v' = v^a / (v^a + (1−v)^a)`,
   `a = 2^contrast`. a = 1 — тождественная; гладкая, без клиппинга,
   середина 0.5 неподвижна. Ползунок ±4 (a от 1/16 до 16).
9. **Насыщенность**: люма в тоновом пространстве `l = 0.2126 vr + 0.7152 vg
   + 0.0722 vb`, потом `v' = l + sat·(v−l)` с клампом. 1 = как есть,
   0 = ч/б, до 4 (отрицательные значения инвертировали бы цвет — не даём).
   Действующая насыщенность — `saturation · cam_sat`: `cam_sat` —
   множитель «как JPEG камеры» (`match_saturation`, производное поле):
   средняя цветность (max − min каналов) встроенного JPEG к нашей
   проявке с камерной кривой, по средним тонам (люма 25..230, ни один
   канал не у 255); насыщенность раздвигает каналы от люмы, поэтому
   отношение средних и есть множитель; пределы 0.8..2. Кривая яркости
   сочности JPEG не даёт — у камеры она в основном от стиля изображения
   (насыщенность). Тест `test_match_saturation` (×1.5 восстанавливается
   ±0.05).
   (Приближение: BT.709-веса применяются к гамма-значениям —
   для насыщенности это стандартная практика.)
9¼. **Сочность** (`vibrance`, −100..100, `vibrance_pixel`) — сразу после
   насыщенности, в тоновом пространстве. `s = (max−min)/max` (HSV),
   множитель насыщенности `k = 1 + a·(1−s)²`, `a = vibrance/100`, каналы
   раздвигаются от люмы, как в п. 9. Блёклые цвета получают почти
   полный множитель, чистые почти не меняются; при −100 блёклое
   приглушается до ~36 % (s = 0.2), насыщенное остаётся. При a > 0:
   защита кожи — в секстанте R ≥ G ≥ B оттенок `h = (g−b)/c` (0..60°),
   палатка с центром 30° и полушириной ~24° снимает до половины подъёма
   (`vib_skin_*`), и `k` ограничен так, чтобы ни один канал не вышел за
   0..255 (сочность не клипает яркие цвета). Серое (размах < 0.5) не
   трогается. На пиксель — только при vibrance ≠ 0: min/max и несколько
   умножений, без таблиц.
8½. **Тональные кривые** (`tc_rgb`, `tc_r`, `tc_g`, `tc_b` — по 256 узлов
   тон 0..255 → тон 0..255, пусто = тождественная): после контраста, до
   насыщенности; сначала общая, затем своя у канала. Живут в таблицах:
   `channel_luts` без канальных кривых вшивает общую в `flut` (одна
   таблица на все каналы), с ними строит три — `tc_c(tc_rgb(flut))`. На
   пиксель ничего не добавляется (три выборки были и раньше). Точки
   кривых и сплайн — в GUI (vgui.CurveEditor, `vgui.curve_lut`).
9½. **HSL-эквалайзер** (`hsl_hue/sat/lum [8]f32`, −100..100) — после
   насыщенности, в тоновом пространстве. 8 диапазонов с центрами
   `hsl_centers` = 0, 30, 60, 120, 180, 240, 270, 300° (тёплых оттенков
   больше, как в Lightroom), между центрами — линейная интерполяция по
   кругу. `build_hsl` раскладывает это в 1024 корзины оттенка: сдвиг
   оттенка (100 = +30°), множитель насыщенности (−100 = ч/б, +100 = ×2),
   множитель яркости (±100 = ±1 EV), флаг `act` (корзина меняется). На
   пиксель (`hsl_pixel`): RGB → оттенок и корзина; неактивная корзина —
   выход; иначе s = C/max, сдвиг оттенка и яркость взвешены s (почти
   серое не трогается, серое с размахом < 0.5 — вообще пропускается).
   Без сдвига оттенка — формула без обратного HSV → RGB:
   `ch' = v/mx · (mx − k·(mx − ch))`; со сдвигом — полный HSV → RGB.
   Стоимость на превью IMG_0991 (6 Мп, -prod): кривые +2 мс, HSL ~+100 мс
   (зелень кадра почти вся «активна»), без -prod ~+230 мс —
   пересчёт только по отпусканию ползунка.
10. **Дизеринг (квантование в 8 бит)**: `v'` из шага 9 округляется в u8
    (`int(v+0.5)`, не обрубание) с добавкой TPDF-шума ±1 LSB — иначе на
    гладких градиентах (небо) видны полосы (banding), как без дизера в
    darktable/RawTherapee. Шум — разность двух независимых сэмплов LCG
    в [0,1) (треугольное распределение), свой на каждый канал (6 шагов
    LCG на пиксель), детерминирован по индексу пикселя (воспроизводимость
    тестов, никакого стейта между вызовами). Включён по умолчанию
    (`Params.dither = true`), отключаем для тестов, которым важна точная
    побайтовая проверка (яркость/монотонность/сравнение кривых) —
    дизер намеренно не входит в эти инварианты, только в собственный тест.
    Стоимость — 6 целочисленных LCG-шагов и пара сложений на пиксель,
    без powf — вписывается в бюджет ~50 мс на превью.

11. **Резкость** (`sharpen.v`, только `apply_image`, при
    `sharp.amount > 0`) — после HSL, перед квантованием; см. ниже.

**«Тени/Света» (как в RawTherapee)** — отдельный множитель к шагу 6:
`sh_shadows`/`sh_highlights` 0..100, но тоновая позиция берётся из
РАЗМЫТОЙ люмы окрестности (`blur_luma`: BT.709-люма + тройной box blur,
радиус ~1% большей стороны). Соседние пиксели получают почти одинаковый
множитель — локальный контраст сохраняется, подъём теней не даёт «плоской»
картинки (в отличие от per-pixel маски шага 4; это и есть главное отличие
инструмента RT). 100 теней = +3 EV в черноте (маска (1−t)²), 100 светов =
−2 EV в белом (маска t²). Маска зависит только от сырья: считается один раз
на кадр (после коррекции объектива!), в `apply()` передаётся указателем
(nil допустим — параметры игнорируются). Третья LUT `slut[yb]` → на пиксель
добавляется одна выборка и одно умножение.

### Многопоточный рендер (05.10.2026)

`render` строит таблицы (тон, кривые, HSL с цветовой таблицей, дымка,
«Тени/Света») один раз и режет пиксели на полосы по числу ядер (`bands`,
до 16; меньше 250 тыс. пикселей — один поток): `render_rows(&RenderCtx,
i0, i1)` — обычная функция, не замыкание (post.v). Пиксели независимы,
дизер — по номеру пикселя, поэтому результат байт в байт как однопоточный
(`test_render_threads_match`). Превью 6 Мп: 70 → 19 мс, с цветовой
таблицей 147 → 30 мс.

### Почему живые ползунки: LUT-структура

Шаги 1–8 на пиксель стоили бы 4–6 `powf` — ~0.5–1 с на 6 Мп. Вместо этого
две таблицы, перестраиваемые при каждом вызове `apply()` (~130К powf ≈ 2–4 мс):

- `mlut[y]` (65536 × f32): линейная люма u16 → общий множитель `k`
  (экспозиция + тени + эквалайзер). Вся зависимость от люмы — здесь.
- `flut[x]` (65536 × f32): линейное значение канала u16 → тон 0..255
  (гамма + контраст). Вся нелинейность канала — здесь. С камерной кривой
  она смешанная (по каналам и по люме, п. 7½), и `flut` заменяют
  `CamTone` и таблица тон → тон `build_post`.

На пиксель остаётся: целочисленная люма (3 умножения), `k = mlut[y]`,
3 умножения `c·k` с клампом 65535, 3 выборки `flut[...]`, насыщенность
(6 умножений, пропускается при sat == 1). Итог: превью 3000×2000 за ~50 мс,
полный кадр 24 Мп ~200 мс. 65536 f32 = 256 КБ на таблицу — влезает в L2.

Важно: индексация `flut[int(f32-значение)]` корректна потому, что перед ней
кламп к 65535.0; `mlut` индексируется люмой ДО экспозиции (E внесён в таблицу).

### Баланс белого (wb.v)

Сырьё LibRaw уже с камерным ББ: `out = rgb_cam · diag(m_shot) · raw`. Под
другой источник (T, оттенок) нужны множители `m_T = 1 / (cam_xyz · XYZ_T)`
(белое под этим светом становится нейтральным), поэтому матрица по
готовому сырью `M = rgb_cam · diag(m_T / m_shot) · rgb_cam⁻¹` — точнее
простых множителей RGB, перепроявка LibRaw не нужна (ползунки живые).
Множители нормированы по G. XYZ источника: кривая Планка (кубическое
приближение Kim et al., 1667..25000 K), оттенок — сдвиг поперёк неё в
CIE 1960 uv на `tint/3000` Duv (шкала Lightroom/DNG SDK; плюс — источник
зеленее → картинка пурпурнее). `CamColor` — данные камеры (`raw.color()`);
без матриц (неизвестная камера) — запасная модель «камера = sRGB».
- `wb_matrix(T, tint)` — M целиком (тесты), `wb_xform(T, tint)` — то же
  по шагам для пайплайна (`WbXform`: `cam` = rgb_cam⁻¹, `d` = m_T/m_shot,
  `rgb` = rgb_cam, `g`, быстрый путь `m`, `lim`), `as_shot()` — T/оттенок камерного ББ (обратная
  задача: отклик `1/m_shot` → XYZ → uv → ближайшая точка кривой перебором
  по майредам + тернарное уточнение, оттенок — знаковое расстояние);
  `neutral_temp_tint(r, g, b)` — настройки, при которых цвет превью «как
  снято» станет серым (пипетка, «Авто»); `gray_world` — средний цвет кадра
  без почти чёрного и пересветов (каждый 4-й пиксель). Диапазоны:
  2000..12000 K, оттенок ±150.
- **Светлое — клип в пространстве камеры** (с 30.09.2026, вместо
  прежней «защиты светов»): как проявил бы LibRaw с множителями m_T
  (`user_mul`). На пиксель: `c = cam·in` (камера после ББ «как снято»),
  `o = c·d`, клип каналов o в 65535, `out = rgb·o`. Канал с наименьшим
  множителем «как снято» (`g`, у R8 — G) клипается только на сенсоре:
  когда он у предела (0.98..0.998 от 65535 — вес `sens`), клипнутые
  каналы пикселя (тот же вес по своему значению) плавно уходят в предел
  — пересвеченное на сенсоре белое остаётся белым. Отрицательные
  (вне охвата) не обрезаются — как у матрицы. **Быстрый путь**: при
  max(вход) < `lim` (= 0.98·65535 / max_i Σ_j |cam_ij|·max(d_i, 1)) ни
  один канал не дойдёт до клипа — одной матрицей `m`; стык путей без
  шва (тест). Стоимость ББ на превью ~+18 мс (по шагам везде было бы
  +44). Прежняя защита смешивала матрицу с масштабом выше 90% входа —
  шумное небо у клипа выходило бело-голубыми пятнами. Замер на
  IMG_1115 (небо сквозь ветки, 3000 K), расхождение с проявкой LibRaw
  `user_mul`: на худшем участке R/G/B было 45/14/4 уровня, стало
  3.2/2.5/1.8; по кадру 4.6/3.2/2.8 → 2.6/2.1/2.7. Данные, которые
  срезал камерный ББ ещё в LibRaw (канал с большим множителем клипается
  раньше сенсора), не вернуть — это предел подхода «ББ по готовому
  сырью». LibRaw `user_mul` работает только при `use_camera_wb = 0`.
- «Как снято» у R8 (IMG_0991) — 5600 K / +10; пипетка по бетону — 4650 K.
- Тест `wb_test.v`: «как снято» → тождественная матрица; направление
  (выше T — теплее, плюс оттенка — пурпурнее); пипетка сходится с прямой
  задачей (T ±2 майреда, оттенок ±1.5) и делает цвет серым; запасная
  модель без NaN; тождественная матрица в пайплайне = без ББ; клипнутое
  белое после ББ 3000 K — белое; `wb_xform` = `wb_matrix`, «как снято»
  у клипа меняет ≤2 уровня; голубое небо, синий канал камеры уходит в
  клип — переход без скачков (≤3 уровня между соседями); быстрый путь
  стыкуется с шагами без шва.

### Удаление дымки (dehaze.v)

Как «Удаление дымки» RawTherapee (сила, глубина, карта глубины) и Dehaze
Lightroom. Метод тёмного канала (He, Sun, Tang 2009), модель в линейном
свете `I = J·t + A·(1 − t)`. `haze_map(src, w, h) HazeMap` — раз на кадр
(зависит только от сырья): рабочая копия — среднее блоков до длинной
стороны ~1024 (превью и полный кадр дают почти одну карту);
тёмный канал — минимум по каналам и окну 15×15 (`min_filter`,
разделимый, монотонная очередь); свет дымки A — средний цвет 0.1%
пикселей с самым светлым тёмным каналом (A берётся из неба/самого
туманного — без такого места A занижается); доля дымки — тёмный канал
I/A, уточнённый управляемым фильтром по люме (r 28, eps 2e-4 —
линейная люма, дисперсии малы; `box_mean`); на полный размер —
коэффициенты a, b билинейно, `D = a·люма + b` (быстрый управляемый
фильтр) → u16. На пиксель (`build_hlut`, 65536): D^γ, γ = 2^((25 −
глубина)/25) (25 — без поправки, больше — дымка убирается и ближе к
камере); сила > 0 — множитель 1/t, t = 1 − 0.95·сила·D^γ не ниже 0.1;
сила < 0 — t (дымку добавить). `haze_view` — карта D^γ серым (флажок).
Тест `dehaze_test.v`: синтетическая сцена с дымкой, растущей вправо, и
полосой неба — A найден (±0.12), справа карта ×2 больше, сила 0 = `apply`,
удаление поднимает разброс дальнего плана ×1.5, добавление снижает;
`min_filter`.

### Резкость (sharpen.v)

`apply_image(src, mask, w, h, p, scale, dst, stride)` — пайплайн кадра с
резкостью (ей нужны размеры); `apply` (без размеров) резкость не делает.
При `sharp.amount > 0` проход `render` пишет тоны (0..255 ×256 в u16, без
квантования и дизера) в буфер, затем unsharp mask по люме в ТОНОВОМ
пространстве (как RT по L*: одинаковый ореол у светлого и тёмного края):
L — BT.709 по тоновым RGB, B — гаусс (разделимый, радиус ядра ⌈3σ⌉,
σ = radius·scale, край — повтор), деталь `d = L − B`; порог
`d·d²/(d² + t²)`, t = detail·0.06; маска краёв `·e²/(e² + te²)`, e —
градиент B, te = masking·0.15; добавка `amount/100·d` одна на все каналы
(только по яркости, без цветных ореолов), затем дизер и 8 бит (`put_px`).
Радиус — в пикселях полного кадра, превью half-size — `scale = 0.5`
(`preview_scale`). Память на время прохода: тоны 6 байт/пк + две
плоскости f32. **По каналам RGB** (`sharp.rgb`): деталь каждого канала —
от его размытия (ещё три гаусса), порог — к каждой, маска краёв та же (по
люме); резче края равной яркости и разного цвета (красное на зелёном),
цена — возможные цветные ореолы. **Показ** (`apply_image_view`,
`SharpView`): `mask` — маска краёв серым (белое — резкость действует;
считается и при amount 0), `detail` — добавка резкости ×8 на сером 128
(по каналам — цветная); без дизера. Гаусс — `gauss_kernel` +
`gauss_into` (буферы снаружи, кадр от 250К пк — полосами строк в
`runtime.nr_cpus()` потоков, не больше 16: строки, затем столбцы).
Тест `sharpen_test.v`: amount 0 = `apply` байт в байт,
край контрастнее, вдали от края без изменений и серое серое; порог и
маска давят шум на ровном >2×, край сохраняют ≥60%; гаусс сохраняет сумму;
RGB на сером = по люме (±1), на красно-зелёном крае — красный краснее;
показ маски и деталей (в том числе при amount 0).

### Capture-резкость (deconv.v)

Как «Capture sharpening» RawTherapee: деконволюция Ричардсона-Люси по
ЛИНЕЙНОЙ люме Y (BT.709) — возврат резкости, съеденной оптикой и
демозаикой, без ореолов USM. Это подготовка сырья (как шумодав), а не шаг
LUT-пайплайна: `deconvolve(src, w, h, sharp, scale) []u16` — новый буфер
(0 силы — копия). PSF — гаусс σ = `dc_radius` (px полного кадра, превью ×
0.5, не меньше 0.2); `dc_iters = 20` итераций `est ← est·G∗(Y/G∗est)`
(PSF симметрична — G^T = G). Каждая итерация — два гаусса полосами строк
в потоках, поэлементный шаг слит с проходом по столбцам (`dc_cols`).
Порог контраста (`contrast_mask`): вес m = c²/(c² + t²), c — градиент
сглаженной (σ 0.7) гамма-люмы на пиксель ПОЛНОГО кадра (разность × scale/2),
t = `dc_contrast`·0.0005 — ровное и шумное (небо, кожа, тени) не
трогается. Выход: Y' = Y + a·m·(est − Y), a = `dc_amount`/100, каналы ×
Y'/Y (цвет не меняется), множитель в [0.5, 2]. Замер (-prod, IMG_0991):
превью ~0.62 с, полный кадр ~2.6 с (однопоточно было 1.3 / 6 с — упор в
память); на полном кадре энергия мелкой детали (разность с размытием σ 1)
выросла ×2, звона нет. На вписанном превью эффект мал (σ вдвое меньше) —
оценивать в 100%. Тест `deconv_test.v`: 0 = копия; размытая ступенька
круче ×1.3, вдали от края ±60 из 65535, серое серое; порог 40 меняет шум
ровного поля ≥3× меньше, чем без порога.

### Геометрия: кадрирование и поворот (geom.v)

`Geom` (в `EditState.geom`): `rot90` (четверти по часовой), `flip_h`,
`flip_v`, `angle` (градусы, плюс — против часовой, ±45), рамка `x0..x1`,
`y0..y1` в ДОЛЯХ повёрнутого кадра — одинаково ложится на превью
half-size и полный кадр; `aspect` — производное (высота выхода по ширине,
см. `out_geom` в crop.v). Системы координат: S — кадр LibRaw w×h; V —
после ориентации W0×H0 (сначала повороты на 90°, затем отражения); R —
V, повёрнутый на `angle` вокруг центра, того же размера (углы за краем
V — пустые); выход — рамка в R. `geom_apply(src, w, h, ch, g, crop)` —
новый буфер u16 с `ch` каналами (3 — сырьё, 1 — маска «Тени/Света»);
`crop = false` — весь R (режим кадрирования). Выход → источник — одно
аффинное отображение (`geom_affine` по трём точкам через
`point_to_source`): без поворота — ближайший пиксель (центры на центрах,
точная копия), с поворотом — билинейно, за краем — чёрное.
`geom_rgba` — то же для 8-битного RGBA в выход любого размера (быстрое
превью камеры). Рамка: `CropBox` (пиксели R), `fits` — все углы
обратно в V внутри кадра (нет пустых углов); `fit_toward(from, to)` —
бисекция по пути от допустимой рамки к цели: так ограничиваются перенос,
ручки, новая рамка и поворот (путь сохраняет опору и пропорцию);
`max_box(aspect, cx, cy)` — наибольшая рамка пропорции с центром;
`best_box` — с тем же центром, если не меньше 85% наибольшей по центру
кадра. `horizon_angle(a, b)` — поправка угла, после которой линия a–b
в R станет горизонтальной (или вертикальной — угол линии приводится к
±45°). `resize_rgb` — размер на выход: уменьшение — по площади (доли
пикселей на краях), увеличение — билинейно, разделимо. Замер (-prod):
превью без поворота / с поворотом ~46 / 100 мс, полный кадр ~0.16 /
0.39 с, `resize_rgb` 24 Мп → 2048 ~0.39 с. Тест `geom_test.v`:
тождество, повороты на 90° и отражения на известных пикселях, доли
рамки, поворот на 90° против часовой = три четверти по часовой, прямое
и обратное отображения сходятся при всех ориентациях, `max_box`/`fits`/
`fit_toward`, горизонт (наклонённая поворотом линия возвращается к 0),
`resize_rgb` (шахматка → среднее, ровное поле ровное).
**Резкость на выход** (02.10.2026, `resize_rgb_sharp` → `out_sharpen` в
`sharpen.v`): уменьшение (`resize_rgb_f32`, без округления) усредняет
пиксели и смягчает края — нерезкая маска по люме уже уменьшенного кадра
(σ = 0.6 px выхода, мягкий порог 1 уровень — шум не усиливается, одна
добавка на все каналы — без цветных ореолов), затем одно округление в
8 бит (`quantize_rgb`). Сила по уровням окна «Экспорт» 0.4 / 0.8 / 1.3;
на IMG_0991 → 1600 px мелкие детали (средний |лапласиан|) ×1.15 / ×1.31
/ ×1.50. Тест `test_resize_rgb_sharp`: без силы — как `resize_rgb`, у
ступеньки ореол в обе стороны, вдали от края и на ровном поле — без
изменений.

### Части кадра (region.v)

Для настоящего 1:1 (`detail.v`): `Region` (x, y, w, h; `expand`,
`contains`), `crop_region`, `geom_source_box` (кусок источника, из
которого геометрия читает прямоугольник выхода, с соседями билинейной
выборки), `geom_apply_region` — прямоугольник выхода `geom_apply` из
куска: те же отображение и шаг (накопление `sx += m.a` с начала строки),
поэтому побитово равен вырезке полного прохода. `upsample_region` —
прямоугольник кадра из того же кадра меньшего размера (билинейно, центры
пикселей по долям) для гладких карт; `haze_region` — карта дымки
фрагмента из карты превью (та же A). Тесты `region_test.v` (повороты на
90°, отражения, угол, режим кадрирования, края).

Фильтры подготовки сырья локальные (без статистики по кадру): вейвлет
шумодава — до 30 px (4 уровня B3), ореолы ~7 px, импульсы — соседи;
Capture-резкость итерационная (20 проходов, ядро до 5 px) — формально
до ~200 px, но затухает: с запасом 96 px фрагмент на IMG_0991 совпал с
полным проходом точно (`detail_test.v`).

### Шумодав и ореолы (denoise.v)

**Полосами в потоках** (`nrbands.v`, 06.10.2026): `impulse`, `denoise`,
`defringe` режут кадр на полосы строк (`nr_band_px` = 1.5 Мп, на 24 Мп —
250 строк) с запасом не меньше радиуса фильтра (вейвлет — 32 строки:
2·(1+2+4+8) = 30, ореолы — 8, импульсы — 2); полоса с запасом
копируется, считается прежней функцией (`*_whole`), в выход идут только
её строки. Полосы читают нетронутый вход и пишут в отдельный выход (у
соседней полосы в запасе ещё не обработанные строки), до
`nr_threads_max` = 4 полос одновременно. Результат бит в бит как целым
кадром (тест `nrbands_test.v`: три операции, полосы 1..200 строк, 1 и 3
потока). Зачем: целым кадром вейвлет держал ~34 байта плоскостей на
пиксель — пик памяти экспорта. Замер (-prod, 24 Мп, импульсы + шумодав +
ореолы): 5.0 → 2.3 с, пик шумодава +641 → +315 МБ; экспорт IMG_0991 с
шумодавом 5.9 → 3.8 с, пик +780 → +472 МБ.

Обе операции — подготовка сырья, как коррекция объектива: правят линейный
буфер НА МЕСТЕ до тонального пайплайна, в LUT-пайплайн не входят.
Работа в sqrt-домене (u16 → sqrt f32): пуассоновский шум после корня
примерно равномерен по диапазону — один порог на тени и света
(стабилизация дисперсии). Цвет отделяется обратимо: y = BT.709 по
sqrt-каналам, u = r−y, v = b−y (декорреляция, не колориметрия).

- **`denoise(buf, w, h, luma, chroma)`** (силы 0..100, 0 — ранний выход):
  вейвлет à trous (B3-сплайн (1,4,6,4,1)/16, шаг ×2 на уровень) — как в RT.
  Деталь уровня давится мягким порогом d³/(d²+t²). Люма: 3 уровня,
  t = сила·0.06; цветность: 4 уровня, t = сила·0.12 (цвет реальных сцен
  низкочастотен, давить можно сильнее). Калибровка по ISO 5000 (IMG_0631):
  рабочее 30–60, на 100 люма заметно «пластиковая» — так задумано.
- **`impulse(buf, w, h, strength)`** — импульсный шум (горячие/мёртвые
  пиксели, аналог «Подавление импульсного шума» RT): пиксель, чей канал
  отклоняется от МЕДИАНЫ 8 соседей больше порога t, заменяется этой
  медианой. Каналы независимы (горячий пиксель часто одноканальный),
  порог t = 55 − сила·0.5 в sqrt-домене (сила — чувствительность; большие
  значения могут съесть звёзды/блики). Два прохода: демозаика размазывает
  выброс в пятно 2–3 пк, второй проход добивает центр. Резкий край
  выживает (медиана соседей — на его стороне перепада), но острые углы
  контрастных объектов при большой силе слегка скругляются. Скорость —
  дешёвый отсев до сортировки: медиана лежит в [min, max] соседей, и если
  оба в пределах t от центра, пиксель точно не импульс (сортировка
  достаётся долям процента). Применяется ДО denoise — вейвлет размазал бы
  выброс по уровням. На чистом кадре меняет <1% значений.
- **`defringe(buf, w, h, strength)`**: цветная кайма = высокий градиент
  люмы И цветность резко выбивается из окрестности → цветность
  подтягивается к размытой (два уровня B3, радиус ~6). Веса гладкие:
  e/(e+6) по контуру, m²/(m²+9) по отклонению. Однородные цветные
  области не трогаются (их цветность равна размытой).
- V-грабля: `mut`-аргументы-скаляры запрещены (`fn lcg(mut seed u32)` —
  ошибка компиляции), только массивы/структуры/указатели/интерфейсы.
- Тест denoise_test.v (LCG-шум, детерминирован): сила 0 = тождественность,
  дисперсия шума ↓3×+, средние и резкий край сохраняются, цветной шум ↓4×,
  кайма обесцвечивается ≥2×, цветное пятно вдали от края цело; impulse —
  горячий/одноканальный/мёртвый пиксели вернулись к фону, изменено <2%
  пикселей, перепад края ≥95%.

### Тест pipeline_test.v — инварианты

Серый градиент: нейтральные параметры → монотонность, серое остаётся серым,
0→0 и 65535→255; экспозиция +1 EV светлее в середине; тени поднимают тёмное,
белое не трогают; контраст: тени темнее + света светлее; насыщенность 0
обесцвечивает; подъём средней полосы EQ светлит середину, белую точку не трогает.
При изменении формул тест — первая проверка, что ничего не сломалось.

## Модуль ai/ — нейросетевой шумодав (ONNX Runtime)

- **Раскладка (переносимо, без установки)**: всё скачиваемое — рядом с
  программой, `ai.places(root)`: `models/` — файлы моделей,
  `onnxruntime/` — ONNX Runtime (содержимое официального архива: `lib/`,
  лицензии). В приложении root = `app_dir()` (папка бинарника), в тестах —
  `@VMODROOT` (корень проекта, где и собирается `./vraw`).
- **Каталог** (`catalog.v`, `ai.models`): `ModelInfo` — id (ключ в
  настройках и сайдкаре), имя, описание, файлы (`ModelFile`: имя, URL,
  размер, sha256; первый — сам `.onnx`), секунд на плитку (для оценок),
  лицензия. Все модели — вход/выход 1×3×h×w float, sRGB 0..1, имена
  входа/выхода берутся из модели:
  - `scunet_real_psnr` (по умолчанию) и `scunet_real_gan` — SCUNet
    (cszn/SCUNet, Apache-2.0), «blind real-world» веса, готовые ONNX с
    huggingface.co/Heliosoph/scunet-onnx: граф `.onnx` (3.8 МБ) + веса
    `.onnx.data` (73 МБ) рядом (ORT находит сам). ~2 с на плитку.
    GAN-вариант дорисовывает текстуру — меньше «мыла».
  - `nafnet_sidd_w32` — NAFNet-SIDD-width32 (MIT), 117 МБ, 0.33 с на
    плитку, но мылит мелкие детали и даёт вертикальные полосы в тёмном.
    URL нет (готового ONNX в сети нет): только свой экспорт
    `tools/nafnet_export.py` из официальных весов.
  `installed(p)` — все файлы на месте нужного размера (sha256 — только
  при скачивании). `runtime_lib(p)` — `onnxruntime/lib/libonnxruntime.so.1`.
- **Скачивание** (`install.v`): `install_runtime` (архив 11 МБ с GitHub,
  sha256, распаковка системным `tar --strip-components=1` во временную
  папку и переименование), `install_model` (файлы, уже лежащие целыми,
  пропускаются). Файл качается в `.part`, на место — только при
  совпадении размера и sha256 (сумма — потоково по готовому файлу).
  **Докачка**: при обрыве `.part` остаётся, запрос повторяется с
  `Range: bytes=N-` (до 5 попыток, пауза 1..4 с с проверкой отмены);
  не вышло — `.part` ждёт следующего «Скачать». 200 вместо 206 — файл
  заново; 416 — `.part` удаляется; не сошлась сумма после докачки — один
  раз с нуля. Отмена (progress вернул false) удаляет `.part`, ошибка
  `Cancelled`. Грабли V (0.5.2): HTTP/2-клиент качает большие файлы в
  десятки раз медленнее — `enable_http2: false`;
  `download_file_with_progress` пропускает куски ответа 206 — поэтому
  `http.fetch` с `on_progress_body` (статус приходит в callback).
- **ONNX Runtime 1.30** не линкуется: `dlopen` по пути (`load_runtime`,
  один раз за процесс, под мьютексом), нужен один символ `OrtGetApiBase`,
  остальное — таблица `OrtApi`. Без библиотеки vraw работает (нет AI).
  Заголовки для сборки — `ai/include` (из официальной сборки 1.30, MIT,
  `LICENSE-onnxruntime`). C-прослойка `ai/ort_shim.h` (static-функции):
  загрузить библиотеку и создать общую `OrtEnv` (одна на процесс, на все
  модели), открыть модель (оптимизация графа ALL), прогнать тензор
  (данные без копий — `CreateTensorWithDataAsOrtValue`), закрыть.
- **`Cache`** — одна модель: грузится (вместе с ORT) один раз за запуск
  при первой надобности (~1.5 с), под мьютексом (превью и экспорт — разные
  потоки); ошибка загрузки запоминается. Session.Run потокобезопасен.
  В приложении — по `Cache` на модель (`st.ai_caches`).
- **`denoise(model, src &u16, w, h, progress)`** — весь кадр плитками
  256×256 с перекрытием 32: позиции равномерные (`positions`, шаг ≤ 224,
  последняя вровень с краем), за краем кадра — повтор крайнего пикселя.
  Веса сшивки — трапеции со скатами на внутренних краях, **нормированные
  по каждой оси** (`axis_weights`): в каждой точке сумма весов 1, в 2D —
  произведение, поэтому буфер сумм весов не нужен, швов нет. Вход модели
  — sRGB-гамма (таблица 65536 f32), выход — обратно в линейный u16
  (таблица 65536 по гамме в u16-шкале). Накопитель f32 на кадр (12 байт/пк,
  ~290 МБ на 24 Мп). `progress(done, total)` после каждой плитки; false —
  ошибка `Cancelled` (`err is ai.Cancelled`).
- **`blend(buf, den, s)`** — сила: `buf + (den − buf)·s`, s = 1 — копия.
- **Плитки по отдельности** (`tiles.v`, 06.10.2026, для AI на 1:1):
  `Grid` (`new_grid(w, h)`) — те же позиции и веса сшивки, что у прохода
  по всему кадру; `cover(r)` — плитки, задевающие прямоугольник,
  `window(t)` — часть кадра, которую они читают; `TileCache` — выходы
  модели по плиткам (sRGB f32, 768 КБ на плитку, bigbuf): `fill` досчитывает
  недостающие (прогресс, отмена — посчитанное остаётся), `compose(r)` —
  прямоугольник из плиток, `trim(max)` — вытеснение давно не нужных.
  `denoise_into` теперь сам идёт через `fill_input` / `accumulate` /
  `finish` — те же функции и тот же порядок сложения, поэтому фрагмент из
  плиток равен той же области полного прохода бит в бит (тест
  `tiles_test.v` с поддельной моделью: `Runner` — интерфейс прогона
  плитки, его реализует `Model`; `denoise_with(runner, ...)`).
- Почему так (прототип 27.09.2026, i5-1235U, IMG_0634 ISO 5000): NAFNet

- Тест `ai_test.v`: позиции, сумма весов = 1, гамма туда-обратно, blend;
  каталог (уникальные id, размеры, sha256, https); все скачанные модели

## Модуль bigbuf/ — большие буферы вне сборщика мусора (05.10.2026)

Boehm (сборщик V) освобождённую память системе не отдаёт: ни у готовой
`thirdparty/tcc/lib/libgc.a`, ни у собранной из исходников
(`-d use_bundled_libgc`, USE_MUNMAP) `GC_gcollect_and_unmap` не вернул ни
байта. После экспорта полного кадра процесс оставался при ~1.8 ГБ и рос с
каждым экспортом. `-gc none` не годится: тогда не освобождается ничего
(+280 МБ на переключение кадра).

`bigbuf.new_f32/new_u16/new_u8(n)` — обычный массив V, данные в
анонимном `mmap` (нули), флаги `nofree | nogrow | noslices`;
`bigbuf.free(mut a)` — `munmap` (память сразу у системы), массив пустой;
для массива сборщика (не отсюда) — просто забывает его, так что можно
освобождать результат, который бывает и тем и другим. `is_big` —
выделен ли здесь. Правила: освобождать ровно один раз, после — не трогать
ни массив, ни его копии; `<<` — паника (nogrow), `clone()` — обычный
массив сборщика. Сборщик эту память не сканирует (в пикселях указателей
нет). Тест `bigbuf_test.v`: 10 × 200 МБ без роста RSS.

Где используется — полный кадр 1:1 (`DetailSrc.dev`, ~150 МБ, держатель
— `DetailCtl`, `free` при смене кадра или пересветов), полный JPEG камеры
(`raw.decode_jpeg`), плитки AI на 1:1 (`ai.TileCache`), полосы шумодава
(`nrbands.v`) и временные плоскости (выделение + `defer { free }`):
шумодав (`to_yuv_sqrt`, à trous, импульсы, ореолы), Capture-резкость
(`deconvolve`, `contrast_mask`), резкость (`apply_image_view`,
`sharpen_tone`, `out_sharpen`), `gauss_blur` (результат — bigbuf,
освобождает вызывающий), `blur_luma`, ресайз на выход
(`resize_rgb_f32`), lens (`vign_lut` — карта усиления, `geometry` —
копия для ремапа), `ai.denoise` (накопитель). Экспорт берёт варианты
`_into` с буфером из bigbuf (см. «Сохранение — в фоновом потоке»).
Буферы кадра в превью (State, кэш кадров) — тоже bigbuf, с владельцем
(`bufown.v`, ниже); в сборщике остались карта дымки и 8-битные картинки
(холст, до/после).

### Владение буферами кадра (bufown.v, 05.10.2026)

Сырьё превью (`dev_linear`, `raw_linear`, `linear`, `mask`, `glin`,
`gmask`), результат AI (`ai_linear`) и JPEG камеры (`cam_view`) — в
bigbuf, освобождаются системе, когда их больше никто не держит. Буферы
делятся (без коррекции объектива `raw_linear` — тот же массив, что
`dev_linear`; без шумодава `linear` — тот же, что `raw_linear`; `glin`
без геометрии — тот же, что `linear`; кэш кадров держит те же массивы),
поэтому владение — счётчиком: реестр «адрес данных → число держателей»
под мьютексом (`own_refs`). `own_new[T](n)` / `own_clone` — новый буфер,
одна ссылка; `share(a)` — ещё один держатель; `drop(mut a)` — держатель
отпускает (массив пустеет), последний — `bigbuf.free`; перенос
(`st.linear = res.linear`) — без share/drop. Массив не из реестра
`share`/`drop` пропускают (старый код и тесты как раньше).

Держатели: поля State; запись кэша кадров (`frame_store` — share,
`frame_evict` — drop); итог воркера в пути (`LoadResult`, `PrepResult`,
`AiResult`; не нужен — `free_load`, `drop_prep`, `ai_take`); задание
воркера, пока он читает: `make_prep_job` — share `src`/`ai_src`,
`prep_compute` их отпускает; `ai_check` — share `src`, `ai_worker`
отпускает. Так главный поток может сбросить кадр, пока воркер ещё читает
его сырьё. `prep_compute`: у каждого поля итога своя ссылка (совпадающие
слои — share), промежуточное, не вошедшее в итог, отпускается (тест
`test_prep_ownership` — все 8 сочетаний объектив/шумодав/резкость, реестр
после — пуст).

**Ловушка V (найдена здесь):** `arr << s` и `for c in arr` для структур
с массивами в `mut:`-полях **копируют эти массивы** (в кучу сборщика);
присваивание `mut r := s`, литерал, spread, `<<` структуры без `mut:`
полей — не копируют. Кэш кадров поэтому — `[]&FrameCache`: сначала
`st.fcache << fc` копировал сырьё каждого кадра (~130 МБ в сборщике на
кадр), а настоящие буферы оставались без держателя навсегда.

Замер (33 переключения 12 кадров 24 Мп туда-обратно, рабочая сборка):
до сегодняшних правок — 1050 МБ в конце; кэш выключен — 745 МБ; кэш
включён (10 кадров ≈ 970 МБ сырья) — 1852 МБ и дальше не растёт;
выключение кэша в настройках — 1741 → 775 МБ сразу. Куча сборщика с
кэшем — ~33 МБ живого. Как мерить: RSS из `/proc/<pid>/status` после
шагов (XTest-нажатия ←/→), разбивка — `GC_get_heap_size/free_bytes`
после `GC_gcollect`, `mallinfo2`, живые объекты сборщика —
`GC_enumerate_reachable_objects_inner` (под `GC_alloc_lock`; из
обработчика в рабочей программе — держит блокировку, программа потом не
выходит), место выделения — gdb с точкой на `GC_malloc` при `$rdi` >
30 МБ (libgc без отладочной информации — размер в регистре).

Замер (экспорт IMG_0991 с шумодавом, обеими резкостями, дымкой и
поворотом, три раза подряд): было пик 2.13 → 2.43 ГБ, RSS после
1.75 → 2.05 ГБ (рос); стало пик 1.36–1.68 ГБ, RSS после ~0.56–0.64 ГБ,
куча сборщика 549 → 621 МБ и дальше не растёт.

## Модуль imgio/ — запись кадра в файл

`imgio.write(path, fmt, w, h, rgb, quality:)` — 8-битный RGB-кадр в
файл. Без vgui (зовётся из save_worker). `Format`: jpeg, png, tiff, bmp,
qoi, gif; у формата — `name()` (для людей), `key()` (в настройках),
`ext()` (новый файл), `exts()` (распознавание и фильтр диалога:
jpg/jpeg, tif/tiff), `lossy()`; `format_by_path` — по расширению без
учёта регистра, `format_by_key`.

- **JPEG, PNG, BMP** — stbi из stdlib V (`stbi_write_*`). PNG у stbi
  сжимает слабовато и медленно (~4 с на 24 Мп, ~53 МБ), зато без
  зависимостей.
- **TIFF** (`tiff.v`, свой) — baseline RGB 8 бит, little-endian, полосы
  по 64 строки, Deflate (Compression 8) с горизонтальным предиктором
  (317 = 2), теги строго по возрастанию, данные по чётным смещениям,
  72 dpi, Software «vraw». Deflate — `C.stbi_zlib_compress` из уже
  слинкованного stbi.o (zlib-поток, как требует TIFF). **Грабля**: буфер
  stb выделяет через V (`stbi__callback_malloc` модуля stbi) —
  освобождать V-шным `free`, `C.free` роняет («free(): invalid pointer»).
- **QOI** (`qoi.v`, свой) — байт в байт как эталонный qoi.h (RGB,
  альфа 255 в хэше).
- **GIF** (`gif.v`, свой) — один кадр, глобальная палитра 256:
  медианное сечение по гистограмме 5 бит на канал (делится коробка с
  наибольшим «число пикселей × протяжённость», по медиане вдоль самой
  длинной оси; цвет — среднее настоящих 8-битных цветов коробки), таблица
  «ячейка → ближайший цвет» на 32768, дизеринг Флойда-Стейнберга
  (ошибки двух строк в одном буфере — присваивать массивы в V нельзя),
  LZW как в gif.h: коды 9..12 бит, сброс при коде 4095, словарь — прямая
  таблица 4096×256 с «поколениями» вместо очистки, EOI — с размером
  кода, который декодер получит после последнего кода. Ограничение
  медианного сечения: цвета палитры — средние, до чистых 0/255 не
  достают, крайние тени и света чуть сдвигаются.
- **EXIF** (`exif.v`, 03.10.2026): `WriteOpts.exif` (`&Exif`, nil — без
  него; `Format.has_exif` — JPEG, PNG, TIFF). Блок — маленький TIFF
  little-endian: IFD0 (Make, Model, Orientation 1, Software, DateTime —
  дата записи, Artist, Copyright, ссылка 34665) и Exif IFD (ExposureTime —
  1/N короче секунды, FNumber, ISO, ExifVersion 0232,
  DateTimeOriginal/Digitized, FocalLength, LensMake, LensModel); пустые
  поля не пишутся. Общий построитель IFD (`IfdEntry`, `put_ifd`: теги по
  возрастанию, данные длиннее 4 байт — сразу за IFD по чётным
  смещениям; `ifd_size` — чтобы заранее знать смещение Exif IFD) — им же
  теперь пишет и `encode_tiff`. JPEG: stb пишет файл (APP0 нет), затем
  `add_exif` перечитывает и вставляет APP1 «Exif\0\0» сразу за SOI; PNG
  — чанк eXIf (CRC — `hash.crc32`) сразу за IHDR; TIFF — теги EXIF в IFD
  кадра, Exif IFD следом (`put_exif_ifds`). Тест `exif_test.v`: свой
  мини-читатель IFD (порядок тегов, чётные смещения, значения), JPEG —
  за сегментом тот же поток, PNG и TIFF читаются как прежде. Вручную —
  exiftool без предупреждений, значения экспорта IMG_0817 совпадают с CR3.
- `#flag -Wl,--no-as-needed -lm` в `imgio.v` — та же грабля с libm, что
  в `raw/thumb_test.v` (без неё тест модуля линкуется запасным
  компилятором).
- Тест `imgio_test.v`: PNG/BMP/TIFF/QOI — байт в байт (PNG/BMP читаются
  stbi, TIFF и QOI — своими мини-декодерами в тесте, TIFF — полосы 1..4);
  GIF немногих цветов (разные 5-битные ячейки) — байт в байт (LZW со
  сбросами словаря); GIF градиента — средние по блокам 8×8 в пределах 3
  (вдали от краёв гаммы); JPEG — близко. Вручную проверено Pillow: все
  шесть форматов открываются, PNG/TIFF/BMP/QOI дают одинаковые пиксели.

## GUI (app.v)

- **State**: `dev` (LibRaw), три слоя сырья превью: `dev_linear []u16`
  (прямо из LibRaw), `raw_linear` (после коррекции объектива, ДО шумодава),
  `linear` + `pw, ph` (рабочее сырьё пайплайна); `mask []u16` (размытая
  люма для «Тени/Света», ~0.35 с на превью; save_worker считает свою для
  полного кадра). Слои, которые ничего не меняют, — ОДИН массив на
  несколько полей (05.10.2026, −80 МБ живой памяти превью 24 Мп):
  `prep_compute` копирует сырьё только под правку — без коррекции
  объектива `raw_linear` = `dev_linear`, без AI, шумодава и Capture

  и обрезки) — `glin` = `linear`, `gmask` = `mask`. Поэтому буферы State
  только читаются: править на месте нельзя (подготовка, AI-прогон и
  1:1 берут их без копии); новый слой — новый массив. `edit EditState` (все настройки правки кадра, см.
  «Неразрушающее редактирование и история»), `quality`, `suppress bool`.

  `prep_threads`, `prep_done`.

  4 с, у ошибок 6 с) — needs_animation руками не нужен.
- **load_preview(..., async)** — при открытии файла (async = false) и при
  смене режима пересветов (async = true): `develop(half,
  highlight)` в главном потоке (~0.1 с), копия в `st.dev_linear`
  (`vmemcpy`, LibRaw-буфер сразу `free()`), `lens_dirty = true`, затем
  подготовка сырья: при async — `request_prep` (фон), иначе сразу
  `prep_compute` (открытию нужна готовая картинка для setup_curve; смена
  размера тоже всегда синхронна — буферы и холст должны совпасть до
  первого apply). Холст пересоздаётся ТОЛЬКО при смене размера
  (`resized`) — перепроявка того же файла не сбрасывает зум/панораму.
- **Подготовка сырья — в фоне** (коррекция объектива, импульсы, шумодав,
  ореолы, маска; до ~3.5 с на превью). `prep_compute(PrepJob) PrepResult`
  — чистая функция без State/vgui: при `redo_lens` берёт копию
  `dev_linear` и корректирует объектив (результат → `raw_linear`), иначе
  копию `raw_linear`; дальше impulse → denoise → defringe → Capture-резкость
  (`deconvolve`, в новый буфер — он и есть `linear`) → blur_luma (по сырью
  до деконволюции).
  `request_prep(redo_lens)` снимает PrepJob (`make_prep_job`, копии
  буферов) и `spawn prep_worker` → результат через `app.post` в
  `st.prep_done` (главный поток): `take_prep` + apply. **Воркер всегда
  один**: запрос во время работы только меняет настройки (`lens_dirty`,
  nr-значения); prep_done сверяет их с применёнными (`nr_applied`) и при
  расхождении запускает ещё один проход — быстрые клики схлопываются.
  Capture-резкость сверяется так же: `dc_applied` — `dc_key(sharp)` (сила,
  радиус, порог; при силе 0 — нули) последней подготовки, `prep_stale`
  сравнивает и её.
  `st.corr` воркер делит с GUI, поэтому перед его освобождением (открытие
  файла, выход) — `wait_prep()`; результат дождавшегося воркера
  отбрасывается (`file_gen` сменился / `prep_running == false`).
  Пока воркер считает, тональные ползунки работают по старому `linear`.

### Замыкания и память (05.10.2026)

Две особенности V (0.5.x, gc boehm) делали из каждого замыкания вечную
ссылку на чужую память; вместе — утечка ~140–200 МБ на каждое открытие
кадра (12 переключений — 550 МБ → 2.5 ГБ):

1. Замыкание V не освобождает никогда, вместе со всем захваченным
   (`app.post(fn [res] ...)` держал `LoadResult` с четырьмя буферами
   превью). Освобождение — только явным API `closure.Lifetime`.
2. Каждое созданное замыкание V пишет в глобальную таблицу
   `g_closure.live` запись `ClosureLiveInfo{ctx, owns_data bool,
   drop_data, generation}`. В -prod gcc пишет в `owns_data` один байт
   (`movb $0x1`), а в таблицу копируются все 32 — семь байт выравнивания
   несут мусор со стека потока. Таблицу консервативный сборщик сканирует:
   мусор, похожий на указатель внутрь буфера (`адрес|01`), держит буфер
   до выхода. Найдено дампом памяти работающей vraw; отдельное
   воспроизведение (20 мёртвых буферов по 20 МБ: без замыканий живо 20 МБ,
   с замыканиями — 400 МБ; без -prod утечки нет) — отчёт vlang/v#29468
   (05.10.2026). Исправят — обход можно оставить: он и так дешевле.

Правило: в повторяющихся местах замыканий не создавать.
- `post_result[T](mut app, on_done, val)` (post.v): результат и приёмник —
  в `Mailbox[T]` (куча), в очередь `parcel_queue` (мьютекс) — указатель и
  `deliver_mailbox[T]` (обобщённая функция — обычная, не замыкание);
  `app.post(drain_parcels)` — функция без захватов. Приёмник забирает
  значение и опустошает ящик; очередь после выдачи затирается целиком
  (сборщик видит и хвост за len). `report` — то же для итога сохранения
  (`Report` + `deliver_report`).
- Прогресс — интерфейсами: `ai.Progress` (`step`; `ai.denoise(..., mut
  p)`), `StageProgress` (`stage`; `ExportOpts.progress ?StageProgress`,
  `AiStage` — плитки AI как этап `.ai`); реализации шлют `post_result`:
  `AiPoster`, `ExportPoster`, `BatchPoster`, `DlTick`.
- Главный поток: приёмники повторяющихся `app.post` — замыкания,
  созданные один раз при запуске (`st.fx_post` для `defer_fx`,
  `st.dt_check`, `st.dt_done` для 1:1); пометка кадров — значением
  `MarkEdit`, не функцией.
- Ячейки ленты кадров (`strip_cell`, browser.v) — из запаса `st.cells`:
  у каждой своё замыкание `on_overlay` с захваченным холстом. Раньше
  `load_folder` создавал их заново на каждую папку — каждая открытая
  папка навсегда оставляла свою ленту (~19 МБ сборщика на 94 кадра плюс
  текстуры; 05.10.2026: смена папок туда-обратно — 0.6 → 2.1 ГБ, с
  запасом — ровно 656 МБ). Теперь память ленты — по самой большой папке.
- Остаются (редкие, по одному на задание): `dl_progress_fn` и
  обработчик тела в `ai.fetch` (скачивание моделей).

Проверка — копия с потоком-монитором (`GC_gcollect`, живое = куча −
свободное): 12 переключений кадра — живое ровно 187 МБ, RSS выходит на
плато ~680 МБ.
